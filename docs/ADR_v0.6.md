# ADR 决策记录 · v0.6

> 每条格式固定：**问题 / 备选 / 选择 / 放弃的理由与代价 / 什么情况会改主意**。
> 评审时这份比代码更能说明判断力——尤其是"主动砍掉"的那几条。

---

## ADR-001 不上 GNN，用 Hawkes 替代"资源流向学习"

**问题**：需要"钱/卡/资源从哪流到哪"，GNN 是最直觉的选择。

**备选**：① 图神经网络（GNN/GAT）② 多元 Hawkes `α_ij` 矩阵 ③ 手工维护的产业链图谱

**选择**：②。

**放弃的理由与代价**
- 边规模差 1–2 个量级：本系统几千节点、万级边，GNN 的优势区间在 10⁵ 以上
- 标签差 1–2 个量级：没有足够的"流向"标注
- **任务方向相反**：我们要"发现异常"，GNN 的邻域聚合倾向平滑异常
- 代价：失去端到端学习能力，需要人工设定 kind 划分

**什么情况会改主意**：事件量稳定 > 10⁵ 且积累 ≥ 500 条人工标注流向。

## ADR-002 检测层不用 LLM

**问题**：LLM 能"解释异常"，是否让它直接判断"什么是异常"？

**备选**：① LLM 直接判定 ② 确定性统计（Hawkes/缺口/异常检测）+ LLM 只解释

**选择**：②。

**放弃的理由与代价**
- 可复现性：同样的输入 LLM 每天给不同结果，**无法做 ablation**
- 成本：每天全量判定比只解释贵一个量级
- 代价：统计层只能发现"形态异常"，发现不了"语义异常"（如"这个措辞不对劲"）

**什么情况会改主意**：需要语义级异常，且能接受不可复现——那时应做成独立的"语义异常"通道，与统计通道并列而非替代。

## ADR-003 全嵌入式，放弃 Postgres / pgvector / Docker

**问题**：交付对象是客户单机 Mac，且明确"傻瓜式、开机即用"。

**备选**：① Postgres16 + pgvector + Docker Compose ② SQLite(WAL) + numpy 暴力检索

**选择**：②。

**放弃的理由与代价**
- 任何外部进程都会变成未来的技术支持工单
- 3 年 5 万条 claim × 1024 维 ≈ 205MB 内存，暴力检索 20–40ms；ANN 的价值在 1e6 以上，本系统天花板 1e5
- 代价：失去并发写、失去 SQL 高级特性、ANN 需要手写

**什么情况会改主意**：向量数 > 2e5 或单次检索 > 200ms（阈值写在部署方案 §3）。

## ADR-004 用默认浏览器，不用 pywebview 原生窗口

**问题**：客户期望"一个 app"，原生窗口更像 app。

**备选**：① pywebview(WKWebView) 原生窗口 ② 起本地端口 + 默认浏览器打开

**选择**：②。

**放弃的理由与代价**
- pywebview 硬依赖 pyobjc（+80MB），且 PyInstaller 打包易碎
- 浏览器方案零第三方依赖、跨 macOS 版本稳定、调试容易
- 代价：**观感上不完全像原生 app**（有浏览器地址栏）；菜单栏常驻也做不到

**什么情况会改主意**：客户明确要求"不能出现浏览器"→ 加回 pywebview 约 0.5 天。

## ADR-005 舆情下轨用热力条带，不用面积图

**问题**：技术方案 §6.4 原设计是"上轨竖线（发言）+ 下轨面积带（讨论量）"。

**备选**：① 面积带 ② 热力格子（深浅编码量）

**选择**：②。

**放弃的理由与代价**
- 实测数据每日 0–2 条，面积图会退化成**一排孤立的三角山包**，视觉上是噪声不是信号
- 格子图对稀疏免疫：0 是浅色格，有量就深，一眼看出哪几天热
- 代价：失去"连续趋势"的观感；跨主体量级对比不如面积图直观

**什么情况会改主意**：单日条数稳定 > 20 时，面积图重新变得可读。

## ADR-006 预测用统计基线，不用 LLM 生成

**问题**：预测台账要有内容。

**备选**：① LLM 生成产业判断（"某公司 12 月将发布 X"）② 统计命题（"未来 7 天 X 报道 ≥ N 条"）

**选择**：②。

**放弃的理由与代价**
- **不可核对的预测等于没有预测**：LLM 的产业判断无法自动结算，台账会变成永远 open 的垃圾
- 统计命题能被数据打脸 → 能算 Brier → 系统才可能变强
- 代价：命题"没营养"，不能直接当投资观点；客户可能觉得太保守

**什么情况会改主意**：接入可靠白名单信源后，可让 LLM 生成"可核对的事实型命题"（如"某型号将于某日前出现在官网"），但必须走同一套结算器。

## ADR-007 小红书默认关闭，local 模式不实现签名

**问题**：客户可能想要小红书舆情。

**备选**：① 自建采集（登录态 + 签名） ② 默认 off，只留 vendor（商业数据源）

**选择**：②。

**放弃的理由与代价**
- 签名算法随平台改版失效，维护成本无底；且属"绕过技术措施"，有判例风险
- 采集要登录态 = 替客户持有账号，责任结构最差
- 代价：失去小红书一手讨论；只能靠客户买商业数据源

**什么情况会改主意**：客户书面接受风险且自备账号 + 明确要求（此时也应做成"仅本机、只读、可一键撤销"）。

## ADR-008 转载归并用标题指纹，不引入 MinHash-LSH

**问题**：同一条新闻被多家转载时要算 1 条。

**备选**：① MinHash-LSH 内容指纹 ② 标题 Unicode 归一化 + 正文前缀指纹

**选择**：②。

**放弃的理由与代价**
- 实测 9 家媒体之间**互不转载**（全库 0 组同指纹），LSH 是空转
- 标题指纹实现 20 行、零依赖、可解释；LSH 要引入库并调阈值
- 代价：改写幅度大的洗稿识别不了

**什么情况会改主意**：接入公众号后若转载组 > 10%，再考虑内容指纹 + 相似度阈值。

## ADR-009 公众号走「直链直抓 + feed 待配」，不做全量检索

**问题**：公众号是核心信源。

**备选**：① 关键词全网检索（需公众号后台接口作钥匙）② RSS 镜像 ③ 文章直链直抓

**选择**：③ 为主，② 待客户提供 feed，① 后置。

**放弃的理由与代价**
- 实测公共 WeChat RSS 全不可用（wechat2rss 实例空、RSSHub 被墙），但 `mp.weixin.qq.com` 文章页 200 可直抓
- ① 需要公众号后台权限，有账号风险，且"越权使用后台接口"
- 代价：**发现新文章仍需 feed 或人工给链接**；做不到"全网某号一有更新就进库"

**什么情况会改主意**：客户提供 RSS 服务或公众号后台账号（那时 ① 作为"发现雷达"，③ 作为抓取器）。

## ADR-010 证据强度必须上界面

**问题**：图很好看，但 `n=6` 的斜率是噪声。要不要显示样本量？

**备选**：① 只显示结论（好看） ② 显示 n + 口径，样本不足则置灰并标"不作结论"

**选择**：②。

**放弃的理由与代价**
- 不标 n，客户会把报道频次当成产能数据 → 决策错误 → 项目失败
- 标了 n，界面"显得弱"，但**每个数字都能追溯到原文**，这才是情报产品的底线
- 代价：视觉上不再"满屏都是结论"

**什么情况会改主意**：不。这条是红线。

## ADR-011 事件级去重改用「相似度 + 四道闸门」，推翻 ADR-008 的纯指纹

**问题**：ADR-008 定的标题指纹只能抓"一字不差"的转载。客户真实要求是"同一件事多家都报了只留一条"——那是**换个说法**的同一件事，指纹抓不到。

**备选**：① 维持指纹（0 组命中，等于没做） ② MinHash-LSH + 阈值 ③ 中文 bigram 集合相似度 + 硬约束闸门

**选择**：③。

**放弃的理由与代价**
- 实测 1840 条真实数据里，标题指纹命中 **0 组**；换成 bigram 相似度后命中 **122 组 / 1706 起**，其中 109 起是 ≥2 家同报——差异不是参数问题，是方法不对
- 不用 LSH：数据量只有 10³，按自然日分块后是 48 万对，全量比对 3.9 秒，LSH 的索引成本大于收益；且 LSH 分桶后**无法再加硬约束**，而硬约束才是精度的来源
- 纯相似度会错并，实测四类真实陷阱：`深交所`vs`上交所`（0.93）、`涨停板`vs`跌停板`（0.91）、`开盘价106`vs`110`、`每日固定栏目`同名不同天
- 所以是**一票通过 + 四道否决**：对立词 / 交易所互斥 / 日期不同 / 数字无交集 / 公司实体无交集，任一命中即否决
- 代价：**漏并**依然存在。措辞差异大到相似度 < 0.60 的同一件事仍会留两条（如「Databricks 正初步洽谈融资」vs「按 2250 亿美元估值融资」）。这是刻意选的方向——并错会让"几家报道"这个证据强度指标失真，而它正是全系统打分的基础

**什么情况会改主意**：接入公众号后若人工抽查发现漏并率 > 20%，再上向量召回做候选生成（闸门仍保留）。

## ADR-012 周报按公司归类，归属分强弱且只算标题点名

**问题**："按公司归类"听起来简单，但一条「纳指暴跌，英伟达/AMD/博通齐跌」会被算进三家公司，榜单立刻被宏观文章污染。

**备选**：① 只要实体出现就算（召回高，噪声大） ② 只算标题点名（准，会漏） ③ 两者分列：标题点名进榜并排序，正文提及单独计数展示

**选择**：③。

**放弃的理由与代价**
- 实测 ②单独用会漏掉"正文里才是主体"的长文；①单独用会让「港股收盘」这种综述顶到每家公司榜首
- ③ 的排序键是「标题点名事件数 → 媒体覆盖数 → 提及数」，界面同时显示「正文提及 +N」，读者一眼能看出这家公司是"主角"还是"被顺带提到"
- 代表作排序再加两条压制：标题里点名本公司的优先；大盘综述/多段快讯汇总贴靠后
- 代价：多一列数字要解释；口径必须写清楚（界面上就写在标题旁）

**什么情况会改主意**：不。口径不清的榜单比没有榜单更糟。

## ADR-013 预算按「全额 token」计，缓存命中不减免；限流与预算是两件事

**问题**：客户要求「每天不超 5000 万 token，不管有没有命中缓存；频率也限制一下，别一秒十几个并发」。这三个要求容易被实现成一件错事。

**备选**：① 只按 `prompt_cache_miss + completion` 计（省下来的是缓存那部分） ② 按 `prompt + completion` 全额计，缓存命中只作展示 ③ 不设预算，靠限流兜住

**选择**：② + 独立的限流器。

**放弃的理由与代价**
- ①看起来"更准"，但**账单不是这么算的**：缓存命中的 prompt 仍然计入请求量，只是单价低。按 ① 算，界面会长期显示"才用了 3%"，客户月底看到账单纯粹是惊吓。预算是刹车，不是记账本——刹车必须按最坏情况给
- ② 的代价：数字会比"感觉"大。所以界面同时显示「缓存命中 N（仍按全额计入预算）」，让读者知道差额在哪
- ③ 不行：限流控制的是**速率**，管不住**总量**。跑得慢不等于跑得少
- 限流也不能只限并发：线程抢锁顺序不受控，会在一瞬间连放一批。所以是「并发上限 2 + 最小间隔 450ms」两个约束同时成立
- 代价：采集慢一点（实测 27 个源 97 秒 vs 原来 70 秒）。这是应该付的成本——把对方打挂的第二天就没有源了

**口径落地**
- `usage_day.tokens` 存的是全额；`cached` / `reasoning` 两列单独存，只用于展示与对账
- 预算闸门在**每次调用前**检查（不是只在晚报开跑前）：已用 ≥ 预算就抛 `BudgetExceeded`，
  采集照跑、摘要降级为规则——没有模型的系统也得能出简报
- 旧配置里 `token_budget_daily == 300000`（我当初拍脑袋的默认值）自动升到 50,000,000；
  用户自己填过的数字一律不动

**什么情况会改主意**：不。除非客户明确说"按账单金额卡"——那时要引入单价表，是另一个模型。

## 附：主动砍掉/降级的东西（评审时可展开讲）
