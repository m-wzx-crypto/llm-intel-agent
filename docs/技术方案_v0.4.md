## 0. 一句话定位

**一个每日自主运行、带可结算预测台账、输出结构化视觉简报的产业链情报分析师。**

它和「定时任务 + 大模型总结」的区别只有一处，但这一处决定全部：

| 普通方案 | 本方案 |
|---|---|
| 抓 → 总结 → 推送 | 探测 → 抽取 → 融合 → 建图 → 检测 → 判断 → **结算** → 输出 |
| 每天从零开始 | 有状态，昨天的判断是今天的输入 |
| 无法评估好坏 | 每条预测到期结算，产出校准曲线 |
| 输出是文本 | 输出是结构化 payload + 视觉 |

**「结算」这一步是整个系统的技术核心。** 没有它，系统永远不会变强，也无法证明任何模块有用。

## 1. Agent 的每日循环

```
┌─ T0+00 感知 ──────────────────────────────────────┐
│ probe_run        固定词组 × 平台，0 命中也是数据点    │
│ crawl_incremental URL/标题/时间 三元去重            │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+30 抽取 ──────────────────────────────────────┐
│ extract_claims    LLM + JSON Schema → Claim        │
│ extract_charts    研报图表 → 指标序列（可降级）      │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+50 融合 ──────────────────────────────────────┐
│ resolve_entity    别名 → ANN → LLM（三级）          │
│ fuse_truth        EM 联合估计 信源可靠度 × claim真值 │
│ dedupe            MinHash-LSH                       │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+70 建图 ──────────────────────────────────────┐
│ commit_events     双时间轴 append-only              │
│ snapshot          冻结当日快照 (snapshot_id)         │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+90 检测（不依赖 LLM）─────────────────────────┐
│ hawkes_intensity  分支比 n_ij，临界预警              │
│ gap_delta         Δgap = 短缺/供给 密度的变化率      │
│ anomaly           量突增 / 分化突增 / 跨源张力        │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+110 判断（LLM 多跳）──────────────────────────┐
│ propose_predictions  生成候选命题 + 概率 + 截止日    │
│ challenge           自我反驳：找出反证路径           │
│ settle_due          到期预测主动核对白名单信源        │
└──────────────────────┬────────────────────────────┘
                       ▼
┌─ T0+140 输出 ─────────────────────────────────────┐
│ render_payload    按板块配额裁剪 → digest.json      │
│ push              本机通知 / 静态页                 │
└───────────────────────────────────────────────────┘
```

> **`T0` = 当日任务实际启动时刻，默认 07:30**（launchd 触发，见 `部署方案_v0.4.md` §6）。DAG 内一律用相对偏移，**不写绝对时刻**——绝对时刻要在文档与 plist 两处维护，必然漂移；且休眠补跑时绝对时刻毫无意义。
> 整链预算 **T0+140 分钟（2h20m）**，验收目标是「**上午 9:00 前屏幕上有当日结果**」。

**设计要点**：检测层**不用 LLM**。Hawkes、缺口、异常全是确定性计算——可复现、可测试、便宜。LLM 只在最末端做「解释和判断」。这个顺序不能反，反了会导致每天结果不可复现，无法做 ablation。

## 2. 架构分层

```
                     ┌──────────────┐
                     │  调度 DAG     │  launchd 定时拉起 + 进程内自写 DAG(~200行)
                     └──────┬───────┘
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
   ┌─────────┐        ┌──────────┐        ┌──────────┐
   │ 采集层   │        │ 推理层    │        │ 输出层    │
   │ probes  │        │ hawkes   │        │ digest   │
   │ crawlers│        │ queries  │        │ alerts   │
   │ parsers │        │ llm      │        │ html     │
   └────┬────┘        └────┬─────┘        └────┬─────┘
        │                  │                   │
        └──────────┬───────┴───────────────────┘
                   ▼
        ┌──────────────────────────────┐
        │      存储层（全嵌入式）        │
        │ SQLite(WAL) 事件/实体/台账     │
        │ numpy 向量暴力检索（免服务）    │
        │ DuckDB     时序指标 + ASOF     │
        │ CAS(sha256) 原始文档           │
        └──────────────────────────────┘
```

**全嵌入式，零外部服务进程。** 不依赖 Postgres / Redis / 消息队列 / 容器运行时。
这是刻意选择：交付对象不一定有 Docker，任何外部进程都是未来的技术支持工单。
**必要复杂度 ≠ 展示性复杂度。**

> v0.1 曾按 Postgres16 + pgvector 设计，因「傻瓜式交付、开机即用」的硬约束改为全嵌入式。
> 迁移影响见 `部署方案_v0.4.md` §2；能力无损原因见该文 §3。

## 3. 数据模型

### 3.1 三张图 + 两张台账

| 图 | 节点 | 边 | 回答什么 |
|---|---|---|---|
| **fact** | Org / Chip / Person / Dataset / Event | 采购/适配/雇佣/发布/延期/裁员 | 谁做了什么 |
| **narrative** | Thesis / Indicator / Target | supports / contradicts / tracks | 谁在主张什么，用什么指标跟踪 |
| **discourse** | Utterance / Reaction / Coverage / Account | reaction_to / about / quotes | 谁在谈论谁，反应如何 |

**三张图必须分开。** 合起来会导致：券商叙事被当成事实、评论区噪声稀释一手爆料、预测依据不可追溯。

`tension_with` 是跨图边：fact 与 narrative 冲突时挂这条边。**这条边本身就是最高价值的信号**（例：一手爆料「MiniMax 卡有冗余」vs 研报「算力供给收紧」→ 结构性错配）。

### 3.2 核心表（DDL 摘要，SQLite WAL 方言）

```sql
PRAGMA journal_mode=WAL;
PRAGMA foreign_keys=ON;

-- 双时间轴事件（append-only，永不 UPDATE）
CREATE TABLE event (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  t_valid       TEXT NOT NULL,          -- ISO8601 事情发生时间
  t_txn         TEXT NOT NULL,          -- 我们得知时间（入库时间）
  kind          TEXT NOT NULL,          -- purchase/adapt/release/layoff/...
  subject_id    INTEGER NOT NULL REFERENCES entity(id),
  object_id     INTEGER REFERENCES entity(id),
  attrs         TEXT NOT NULL DEFAULT '{}',  -- JSON
  confidence    REAL NOT NULL,
  supersedes_id INTEGER REFERENCES event(id),  -- 修正不改，追加
  source_id     INTEGER NOT NULL REFERENCES source(id)
);
CREATE INDEX idx_event_valid ON event (t_valid, kind);
CREATE INDEX idx_event_txn   ON event (t_txn);

-- claim 层：抽取产物，先于 event（多 claim 才算一个 event）
CREATE TABLE claim (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  doc_id     INTEGER NOT NULL REFERENCES doc(id),
  raw_text   TEXT NOT NULL,
  triple     TEXT NOT NULL,             -- JSON
  t_txn      TEXT NOT NULL,
  stance     REAL,                      -- -1..1，对同一事实的倾向
  verified   REAL                       -- EM 后验
);

-- 快照：所有查询固定在某个 snapshot 上
CREATE TABLE snapshot (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  taken_at     TEXT NOT NULL,
  max_event_id INTEGER NOT NULL,
  metric_hash  TEXT NOT NULL           -- 指标物化视图的 hash
);

-- 预测台账（一等公民）
CREATE TABLE prediction (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  claim_text    TEXT NOT NULL,
  deadline      TEXT NOT NULL,          -- YYYY-MM-DD
  p             REAL NOT NULL CHECK (p BETWEEN 0.01 AND 0.99),
  snapshot_id   INTEGER NOT NULL REFERENCES snapshot(id),  -- 存证据快照，防后视偏差
  basis         TEXT NOT NULL,          -- JSON：证据链 + 似然比历史
  resolution_sources TEXT NOT NULL,     -- JSON 数组，白名单
  state         TEXT NOT NULL DEFAULT 'proposed'
                CHECK (state IN ('proposed','open','resolved_hit',
                                 'resolved_miss','void','unresolvable')),
  resolved_at   TEXT,
  resolved_by   TEXT
);

-- 探测记录：沉默也要有数据点
CREATE TABLE probe_run (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  run_date   TEXT NOT NULL,
  query_set  TEXT NOT NULL,
  platform   TEXT NOT NULL,
  status     TEXT NOT NULL CHECK (status IN ('ok','zero_hit','unavailable','parse_broken')),
  hit_count  INTEGER NOT NULL,
  health     TEXT NOT NULL   -- JSON: http_status, items_parsed, dom_hash
);
```

> **SQLite 的三个必守事项**（踩坑才懂）：
> 1. `journal_mode=WAL` + `busy_timeout=5000`，否则并发写会锁死
> 2. **单写者**：采集/抽取各自任务串行写，读可以并发（WAL 支持）
> 3. 时间统一存 ISO8601 文本（UTC），比较用字符串排序即等价时间序，避免时区陷阱
> 4. **跨进程只能有一个写者**：`--run-daily`（launchd 拉起）与 GUI 可能同时存在，靠 `data.lock` 上的 `flock` 互斥，见 §3.2.1

### 3.2.1 写者约定与跨进程互斥（v0.4 新增）

两个进程都可能想写库：launchd 在 07:30 拉起的 `--run-daily`，和客户刚好双击打开的 GUI。

| 规则 | 实现 |
|---|---|
| 全局写锁 | `~/Library/Application Support/LLMIntelAgent/data.lock`，非阻塞 `flock(LOCK_EX \| LOCK_NB)` |
| 拿不到锁的 `--run-daily` | 立即退出，记 `lock_skip` 到日志，**不排队、不重试**（另一进程正在跑） |
| 拿不到锁的 GUI | 进**只读模式**：显示上次结果，顶部标「数据更新中」，禁用「立即采集」 |
| SQLite | 仅持锁进程可写；GUI 用 `?mode=ro` 连接 |
| DuckDB | **官方限制单进程写**，故只由持锁进程以读写打开；GUI 用 `read_only=True` |

> 为什么必须在架构层写死：SQLite 的 WAL 允许写者排队，**DuckDB 不允许**——两个进程同时读写打开会**静默损坏**文件，不是报错。这是全嵌入式方案唯一真正危险的并发点，不能靠「应该不会同时发生」。

### 3.3 为什么 `supersedes_id` 而不是 UPDATE

这份 PDF 就是例子：「10 月后有大量收购破产公司数据」是 11/21 才被告知的 10 月事件。

- `t_valid = 2026-10-xx`，`t_txn = 2026-11-21`
- 若混成一个 `created_at`，Hawkes 拟合会把「回头看」误当「刚发生」，爆发簇形态全错
- 且预测结算时会用「现在」的信息判「当时」的预测，后视偏差不可逆

**读历史状态 = `WHERE t_txn <= snapshot_taken_at`**。这是唯一的正确姿势。

## 4. 模块清单

### 第一梯队（必须有，且必须有 ablation）

| # | 模块 | 关键技术 | 复杂度 | 验证方式 |
|---|---|---|---|---|
| M1 | 双时间轴事件溯源 | append-only + snapshot 一致性读 | ★★★ | 用 snapshot(T) 回放历史判断，与人工标注比对 |
| M2 | 信源联合估计 | EM：`r_s` 与 `truth(c)` 交替最大化 | ★★★★ | 200 条人工裁决冲突 claim，对比等权投票/人工固定权重 |
| M3 | 实体消歧 | 别名表 → ANN blocking → LLM 裁决 | ★★★ | 300 对标注，报 P/R/F1 + 「自动通过率@精度≥0.95」 |
| M4 | 混合检索 | BM25 ∪ dense ∪ 图2跳扩展 → RRF(k=60) | ★★★ | 50 条「必须两跳才能答」的评测问题，对比纯 dense recall@10 |
| M5 | 校准预测台账 | 状态机 + 主动结算 + Brier/校准曲线 | ★★ | 对比常数基准率、永远 0.5 两条基线 |

### 第二梯队（收益高，依赖数据积累）

| # | 模块 | 关键技术 | 复杂度 | 验证方式 |
|---|---|---|---|---|
| M6 | Hawkes（**MVP 单变量 / 完整版多元**） | `λ_i(t)=μ_i+Σ_j α_ij Σ exp(-β_i(t-t_k))`，MLE | ★★★★ | MVP：单变量 `(μ,α,β)` + 泊松基线(`α=0`)对照，时间外推切分；多元矩阵按 §4.1 门槛 |
| M7 | 滞后因果筛查 | Granger / 迁移熵 + FDR | ★★ | 与 Hawkes `α_ij` 交叉验证，双方法同向才算成立 |
| M8 | 主动采样 | 期望信息增益选 top-N | ★★★ | 对比「按分数排序」的用户点击率 |
| M9 | 研报图表提取 | 图注解析 → VLM 读数 → 源数据反查 | ★★★★ | 20 张图人工读数，报 MAE；趋势方向准确率 |

### 4.1 M6 的落地顺序（v0.4 收敛：MVP 只做单变量）

多元 Hawkes 的 `α_ij` 是 N×N 参数矩阵。第 3 周事件量「几百条」估不出它——不是算法问题，是自由度问题：几十个节点各带待估参数，几百个事件必然过拟合，AIC 也会替你说明它没用。

分层：

| 阶段 | 模型 | 事件量门槛 | 验收 |
|---|---|---|---|
| 阶段 3（MVP） | 每个 `kind` 独立单变量 Hawkes，只估 `(μ_i, α_i, β_i)` | ≥ 200 | 对数似然显著优于泊松（`α=0`）；分支比可解释 |
| 阶段 5（完整） | 多元 `α_ij` 矩阵 | ≥ 1000，且跨 kind 交叉激励有肉眼可见候选 | AIC 优于「加性单变量之和」，且方向与 M7 迁移熵一致 |

**这条收敛不降低说服力，反而提高**：先证明「爆发有自激结构」（单变量够），再谈「钱从哪流到哪」（要矩阵）。反过来做，等于在数据不足时宣称拿到了流向图。

### M6 是替代 GNN 的正确答案

为什么不上 GNN（已论证，写入 ADR）：边规模差 1–2 个量级、标签差 1–2 个量级、**任务方向相反**（要发现异常，GNN 倾向平滑）。

Hawkes 的 `α_ij` 矩阵直接就是「资源和钱从哪流到哪」的有向强度图，**从数据学出来而非手工画**；分支比 `n_ij = α_ij/β_i` ≈1 就是雪崩前夜，天然给出「缺口正在放大」的置信区间。

## 5. Agent 的能力边界

这是「是 agent 而非脚本」的关键设计，也是评审重点。

### 5.1 工具集（agent 可调用的）

```yaml
tools:
  # 感知
  - probe_platform(query_set, platform) -> ProbeResult
  - fetch_doc(url) -> Doc
  - fetch_filing(symbol, form) -> Doc
  # 记忆
  - query_graph(cypher_like, snapshot) -> Rows
  - query_timeseries(indicator, window) -> Series
  - recall(semantic_query, k) -> Claims
  # 判断
  - compute_metrics(entity, metric, window) -> Value
  - propose_prediction(claim, deadline, p, basis) -> Prediction
  - settle(prediction_id, evidence) -> Resolution
  # 输出
  - compose_digest(quota) -> Digest
```

### 5.2 自主权分级

| 级别 | 行为 | 权限 |
|---|---|---|
| A 完全自主 | 抓取、抽取、建图、算指标、生成预测**草稿**、本地归档 | 无需确认 |
| B 提议待确认 | 修改关注清单、新增信源、作废预测、调整配额 | 每日随简报提交提案 |
| C 禁止 | 对外发送、登录他人账号、绕过付费墙、在平台互动 | 硬编码禁止 |

**B 级的设计是重点**：agent 会自己发现「某信源连续 30 天零产出」并提议移除，或者「某个新实体反复出现」并提议加进关注清单。**这种自我维护能力是 agent 的标志。**

### 5.3 记忆结构

| 层 | 存放 | 内容 |
|---|---|---|
| episodic | `event` 表 | 发生了什么 |
| semantic | 三张图 | 知识结构 |
| procedural | `prompt_version` / `rule_version` | 抽取规则、告警阈值（带版本，可回滚） |
| **meta** | `prediction` + `calibration` | **我判断得准不准** |

meta 层是唯一能让系统随时间变强的，其余三层只让它变全。

## 6. 输出：前端是 agent 的输出面

### 6.1 Agent 输出三件 artifact

```
digest.json     ← 前端唯一数据源（结构化，无长文本）
  ├─ meta: {snapshot_id, t, window}
  ├─ gaps:    [{entity, metric, value, delta, ci}]
  ├─ flows:   [{from, to, channel, volume, trend}]
  ├─ panels:  {competitor: [...], zhipu: [...], tangjie: [...]}
  ├─ forecasts: [{claim, p, deadline, bar_len}]
  └─ why:     {每项的路径证据 id 列表}
brief.md        ← 可选，极简（10 行以内，供快速扫读）
alerts.json     ← 事件触发，非定时
```

**关键：`digest.json` 里没有一段"摘要文字"能超过 40 字。** 所有长内容都在 `why` 的证据链里，点开才看。这是「减少文字化」的工程实现——**不是把字变小，而是把文字换成位置和长度**。

### 6.2 三个问题 → 三个视图（不合并）

| 用户问题 | 量的性质 | 视图 |
|---|---|---|
| 哪些缺口正在放大 | 差 + 变化率 | 发散条（需求−供给，配对） |
| 哪些需求正在增长 | 变化率 | 斜率图 + 微型折线 |
| 钱/卡/资源从哪到哪 | 有向流量 | 桑基图（纵向=产业链层级） |

**不用力导向节点图做主视图**：位置无意义（每次抖动不同→无法建立空间记忆）、边多则缠结、无法表达量和时间。

节点图只在下钻到某实体局部邻域时用。

### 6.3 编码预算（硬约束）

- 颜色**只编码异常度**（灰/琥珀/红），不用来区分公司或关系类型
- 粗细编码量，箭头编码方向，位置编码层级
- **一屏 ≤ 20 段文字，≤ 40 个视觉元素**
- 信源等级用透明度（一手实心 / 二手半透明）
- 全部确定性布局，无动画（"一眼看出"的前提是布局稳定）

### 6.4 舆情双轨图

```
上轨  │    ╷         ╷              ╷      ← 唐杰公开发言（稀疏竖线）
```

## 7. 阶段计划

> **口径（v0.4 统一）**：阶段 1–4.5 = **4 周 MVP（22 个工作日）**；阶段 5 = 第 5–8 周完整版。v0.1 的「4 周可迭代」与「阶段 5 在第 5–8 周」并存是口径错误，此处修正。

### 阶段 1（第 1 周）：地基
- `schema` + 双时间轴表结构 + snapshot 机制
- 采集：20 个信源 + probe_run 框架
- 抽取：LLM + fixed schema → 200 条真实 claim
- 标注：**100 条 golden claim**（人工裁决，0.5 天）—— §11 三样之一，v0.1 漏排工时
- **验收**：能从 PDF/网页稳定产出结构化 claim，去重有效；golden set 首跑有 P/R 基线

### 阶段 2（第 2 周）：可查询
- 实体消歧（三级）→ 图建成
- 信源 EM
- 混合检索 + RRF
- **验收**：能回答「谁可能接 Kimi 的算力单」这类两跳问题

### 阶段 3（第 3 周）：会判断
- Hawkes **单变量** + 泊松基线对照（事件量门槛 ≥200；多元矩阵推迟到阶段 5，理由见 §4.1）
- 缺口 Δ / 异常检测
- 预测台账 + 主动结算
- **验收**：Brier 优于常数基准率；校准曲线可读；单变量 Hawkes 对数似然优于泊松基线

### 阶段 4（第 4 周）：会表达
- digest.json 契约冻结
- 三视图 + 舆情双轨 + 预测带
- **验收**：一屏能看出三件事，且每个元素可下钻

### 阶段 4.5（第 4 周末，约 2.5 天）：能交付（macOS）
**不能排到最后一周。** 打包会反向约束技术选型（某库不支持 PyInstaller 就要提前换），越晚发现越贵。

- PyInstaller(onedir) + pyobjc 裁剪 + `.app` 打包 + `codesign --deep` + `.dmg`
- **改用 launchd LaunchAgent**（非进程内调度）：app 不运行也能拉起，休眠错过后唤醒即补跑
- app 双模式：GUI（双击）+ `--run-daily`（headless，launchd 调用，不弹窗）
- rumps 菜单栏图标，关闭窗口不退出进程
- 首启向导 3 步（API key 测试连接 / 预置关注清单 / 首次采集当场跑）
- **错过的运行必须补**：`now - last_success_run_at > 20h` → 立即补跑；`> 72h` 用宽窗口一次覆盖，禁止循环跑 N 次烧 API
- 一键导出诊断包（含 `launchd.log`，脱敏）
- **验收**：干净 Mac（无 Python、无 Docker、无 Xcode CLT）双击即出结果，全程不求助（详见 `部署方案_v0.4.md` §11）

### 阶段 5（第 5–8 周）：自我维护
- 主动采样 + 反馈闭环
- agent 的 B 级提案机制
- ADR + ablation 表 + golden set 扩到 200 条并做回归
- 多元 Hawkes（`α_ij`，门槛 ≥1000 事件，见 §4.1）
- 成本与校准月度复盘（§12 台账 + 校准曲线合并看）

## 8. 不做清单（写入 ADR）

| 不做 | 理由 |
|---|---|
| GNN | 规模/标签/任务方向三条不满足（见 §4） |
| **Docker / 容器化交付** | **客户机器不一定有容器环境**；任何外部运行时都会变成远程工单。详见 `部署方案_v0.4.md` §1 |
| **pgvector / 独立向量库** | 1e5 向量规模下 numpy 暴力检索 20–40 ms 足够；ANN 的引入门槛写在 `部署方案_v0.4.md` §3 |
| 微服务 / k8s | 单机能跑，拆开只有运维成本 |
| 自研图数据库 | 几千节点，SQLite 递归 CTE 足够 |
| Kafka / Flink | 日更场景，批处理延迟可接受 |
| 全量微调 | 结构化输出 + few-shot 够用，收益不可验证 |
| 多智能体编排 | 易做成角色扮演秀；单 agent + 工具 + DAG 更可靠 |
| 力导向主视图 | 位置无意义，违反「一眼看出」 |

## 9. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| 评论区情感判定不稳（中文反讽） | 舆情风向错误 | 抽检覆盖率公布；结论带置信；只报结构性指标（量/分化/背离），弱化绝对情感值 |
| 水军/控评 | 把操作当民意 | 相似度聚集 + 账号特征 + 时间聚集，剔除出统计但保留原始 |
| 微信评论区不可得 | 最大盲区 | UI 显式标注 unable，**不得**以「未监测到」论证「没人讨论」 |
| 研报渠道合规 | 法务风险 | 只存摘要+链接+观点归属；不接灰色全文源 |
| 卖方结构性偏差 | 把立场当事实 | 进 narrative 图且强制带 `proposer`；用结算检验其可靠度 |
| 预测不可结算 | 台账污染 | 允许 `void` / `unresolvable`；不可结算不硬给数 |
| 采集故障伪装成沉默 | 沉默信号不可信 | 平台健康度 + 多平台交叉判定 |
| **LLM 成本失控** | 单日账单不可预期，客户直接停用 | 三道闸门（§12）；**超限降级而非中断** |
| **DuckDB 多进程写损坏** | 数据文件静默损坏，不可恢复 | 写锁 + GUI 只读连接（§3.2.1） |
| launchd 与 GUI 抢锁 | 当日任务被跳过 | `lock_skip` 显式记日志；补跑判断只看 `last_success_run_at`，不看「今天有没有跑过」 |
| 证书 / 公证审批阻塞 | 交付延期 | 打包与签名并行推进；无证书期先出 ad-hoc 内测包（**不交付客户**） |
| 事件量不足即拟合流向图 | 结论看似有据实则噪声 | §4.1 事件量门槛写进验收前置条件 |
| **公众号只做 RSS 导致的覆盖错觉** | 客户以为"全网监测"，实际只盯清单内 N 个号，误判为漏报失职 | **UI 必须常显「当前盯 N 个号」+ 每轮「覆盖 N 词/命中 M 条」**；RSS 是"订阅"不是"检索"，这句话要写进产品文案 |
| RSS 源不稳定（自建 RSS 多依赖后台接口，等于通道 1 换壳） | 掉号、延迟、解析失败 | 公共实例打底 + 付费 RSS 服务补长尾号（几十元/号/年，风险在服务商）；`probe_run` 记 `channel=rss` 与 `parse_broken` |

## 11. 评审时能拿得出手的三样

代码量不说明问题，这三样说明：

1. **ADR**：每个复杂选择一份，格式固定——问题 / 备选 / 选择 / **放弃的理由与代价** / 什么情况会改主意
2. **Ablation 表**：每模块关掉后指标掉多少（例：「关掉图扩展召回，recall@10 0.71→0.48」）
3. **Golden set**：200 条标注 claim，每次改 prompt 跑回归，看 P/R 有无退化

**"主动砍掉 GNN 并给出三条可量化拒绝理由"比"用了 Hawkes"更能说明技术判断力。**

## 12. LLM 成本模型与预算闸门（v0.4 新增）

v0.1 通篇没有成本数字，而这是客户第一个会问的问题，也是「每日全量抽取 + 多跳判断 + 主动结算」最容易失控的地方。

### 12.1 单价假设（参数化，不写死）

| 参数 | 取值 | 说明 |
|---|---|---|
| 输入 | ¥2 / M token（cache miss），¥0.5 / M（cache hit） | 以 DeepSeek 现价档位为例 |
| 输出 | ¥3 / M token | 同上 |
| 落点 | 模型名、单价、上限全部进 `config.yaml` 的 `cost:` 段 | 换模型只改配置，不改代码 |

绝对金额仅用于量级判断，**签约当日价目为准**。

### 12.2 单日用量估算（设计目标）

| 环节 | 调用量 | in / out（token） | 日成本 |
|---|---|---|---|
| `extract_claims` | 400 篇 | 3k / 0.4k | ¥2.88 |
| `extract_charts`（可降级） | 60 张 | 4k / 0.3k | ¥0.53 |
| 消歧 LLM 裁决 | 80 次 | 1.5k / 0.1k | ¥0.26 |
| 判断 + 自我反驳 | 50 次 | 8k / 0.8k | ¥0.92 |
| 到期结算 | 20 次 | 12k / 0.3k | ¥0.50 |
| **合计** | | | **≈ ¥5.1 / 日 ≈ ¥155 / 月** |

含 cache hit 与重跑余量，预算按 **¥8/日、¥240/月** 设。

### 12.3 三道闸门

| 闸门 | 触发 | 行为 |
|---|---|---|
| G1 次数 | 单次运行 LLM 调用 > `max_calls_per_run`（默认 900） | 停增调用，用已有 claim 出简报，页脚标「本次为降级产出」 |
| G2 金额 | 当日累计估算 > ¥8 | 同上，且次日自动关闭 M9 图表提取 |
| G3 月度 | 当月累计 > ¥240 | 只跑 P0 信源 + 结算，**不中断** |

**原则：超预算降级，不中断。** 断一天的台账，比多花几块钱贵得多。

### 12.4 必须留痕

每次运行写一行 `run_cost`：`run_id, calls, tokens_in, tokens_out, est_cost, gate_tripped`。没有这张表，就无法回答「这个月为什么花了 400」——而这正是客户会问的第二问题。
